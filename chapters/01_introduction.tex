\section{Motivation}
\label{sec:motivation}

Autonomous, self-driving vehicles are one of the most visible and
heavily pursued applications of modern robotics, promising to
navigate complex, populated environments without human intervention.
Realising that promise at full scale is costly and safety-critical,
so a common alternative is to first develop and validate the same
core competencies -- mapping, localisation and navigation -- on a
small-scale, QCar platform.

This thesis uses the Quanser QCar for exactly that purpose: a
1/10th-scale, real-wheel-drive, Ackermann-steered research vehicle
equipped with a 2D LiDAR, an inertial measurement unit (IMU) and an
onboard NVIDIA Jetson TX2 compute module \cite{quanser2023qcar}. It
is a physically real, if miniature, self-driving car. The
practical challenges of autonomous navigation can be identified and
solved on it directly, rather than only theorised about.

The project's goal was to build a self-sufficient navigation system
capable of taking the QCar from a given start pose to a given goal
pose in a mapped indoor environment, reliably and without manual
intervention along the way.

Reaching that goal required a complete stack: sensor-driven mapping,
localisation within that map and closed-loop trajectory control. In
contemporary robotics practice, building such a stack begins in
simulation, where repeatable, safe iteration lets a planner be tuned
against a thousand trial runs before it is ever allowed to steer a
physical vehicle. The pattern runs deep enough in the field that
entire open-source ecosystems are built around software that runs,
largely unmodified, against either a simulated or a physical robot.
Three such ecosystems anchor this thesis: the Robot Operating System
(ROS) and its successor ROS~2 \cite{quigley2009ros,macenski2022ros2},
the Gazebo simulator \cite{koenig2004gazebo} and the Nav2
navigation stack \cite{macenski2020nav2}.

Simulation here was never treated as a separate or preliminary
exercise. It was the first of two necessary phases toward one end
goal: a navigation stack validated on the physical QCar. Every
design decision made in simulation -- the vehicle's kinematic model,
its sensor suite, the manoeuvres it was asked to perform -- was made
with the real QCar's actual capabilities in mind, not any capability
convenient only in simulation. The aim was for migrating the
finished stack onto hardware to be a validation step, not a
redesign.

The stack was accordingly built and validated end-to-end in a
Gazebo simulation of the vehicle first, then migrated onto the
physical robot for a second, hardware validation phase. This thesis
reports on both in turn.

\section{Problem Statement}
\label{sec:problem-statement}

At the outset of this project, no navigation stack had yet been
developed for the QCar. The complete pipeline -- sensor-driven
mapping, localisation and navigation -- had to be designed and
built from scratch, not extended from an existing implementation.
The \emph{actual state} was ``no working mapping,
localisation or navigation capability yet built for this project's
QCar setup, in any form''.

The \emph{target state} was two-fold, matching the two phases
described in Section~\ref{sec:motivation}: a complete navigation
stack built and validated end-to-end in simulation, deliberately
designed around the real QCar's actual capabilities rather than any
simulation-only convenience. This same stack was then to be migrated
onto the physical QCar and validated there, reaching goal poses
reliably. Any discrepancy between the two phases was to be identified
and explained and, where practical, corrected or compensated for --
not left as an unexplained residual error.

Reaching that target state required answering four sub-questions,
each of which forms one methodology chapter of this thesis:

\begin{enumerate}
  \item The navigation stack covers SLAM-based mapping, localisation
        and Nav2-based path planning and control. How should it be
        designed and validated end-to-end in simulation, built around
        the real QCar's actual kinematics and sensor suite, so that
        it is a genuine first phase toward hardware operation rather
        than a simulation-only exercise? (Chapter~\ref{ch:sim-stack})
  \item The robot's onboard compute cannot run the same ROS~2
        distribution as the navigation stack. How should the two be
        connected so that the rest of the stack does not need to
        know the difference? (Chapter~\ref{ch:hardware-bridge})
  \item The vehicle exhibits both an unknown gain and a hard
        static-friction non-linearity. How should the mapping from a
        ROS~2 velocity command to a physical actuator signal be
        identified and calibrated? (Chapter~\ref{ch:calibration})
  \item Once bridged and calibrated, does the navigation stack
        actually reach goals reliably on hardware? What residual gap
        between the simulated and physical phases remains?
        (Chapters~\ref{ch:nav-integration} and~\ref{ch:results})
\end{enumerate}

\section{State of the Art}
\label{sec:state-of-the-art}

ROS~2 was designed to address shortcomings of the original ROS that
made it unsuitable for production and safety-relevant use, chief
among them a lack of real-time support and a single-point-of-failure
master node. In their place, ROS~2 replaces ROS's custom TCP
transport with the Data Distribution Service (DDS) publish-subscribe
middleware standard \cite{omg2015dds,macenski2022ros2}.

Gazebo is the long-established open-source robot simulator most
widely paired with ROS/ROS~2 \cite{koenig2004gazebo}, providing
physics simulation and sensor models (LiDAR, cameras, IMUs) against
the same message interfaces a real robot would publish and subscribe
to. This project relied on that property to develop and validate its
navigation stack in simulation before ever running it on hardware.

Nav2 is the de facto standard ROS~2 navigation stack, providing
pluggable costmaps, global planners and local trajectory
controllers behind a behaviour-tree-orchestrated action interface
\cite{macenski2020nav2}. MPPI control, the local trajectory
controller used in this project, samples large numbers of candidate
control sequences and weights them by a differentiable cost function
evaluated over a rollout horizon, which avoids the need for a convex
or otherwise analytically tractable vehicle model
\cite{williams2015mppi}. This suits an Ackermann-steered vehicle
well, since its real dynamics (addressed in
Chapter~\ref{ch:calibration}) turned out to be considerably less
clean than the textbook bicycle model in Chapter~\ref{ch:groundwork}.

Simultaneous localisation and mapping (SLAM) and probabilistic
localisation are similarly well-established techniques here, not
novel contributions of this thesis. Mapping uses Cartographer, a
real-time, submap-based 2D LiDAR SLAM implementation
\cite{hess2016cartographer}; localisation during navigation uses
Adaptive Monte Carlo Localisation (AMCL), a particle-filter approach
to pose estimation within a known map
\cite{thrun2000probrob,thrun2001robustmcl}.

Sim-to-real transfer is most extensively studied in
reinforcement-learning contexts, where a policy trained purely in
simulation is deployed with no further real-world tuning
\cite{zhao2020sim2real}. This project's navigation stack -- SLAM,
AMCL and MPPI -- is classically engineered rather than learned and
is configured identically in both simulation and reality. The
challenges this thesis reports when migrating that stack to hardware
(Chapters~\ref{ch:hardware-bridge}--\ref{ch:nav-integration}) are of
a different, more concrete kind than the reality-gap problem
addressed in that literature. They are specific, individually
diagnosable mismatches between a simulated and a real implementation
of the same explicit model, not a policy's failure to generalise
beyond its training distribution.

\section{Research Gap}
\label{sec:research-gap}

Section~\ref{sec:state-of-the-art} named the tools this thesis builds
on: ROS~2, Gazebo, Nav2, Cartographer and MPPI. None of them were
written or substantially modified here. What none of them provide,
out of the box, is a working answer for this platform's specific
combination of constraints.

No published Nav2 integration handles a vehicle whose onboard compute
cannot run a matching ROS~2 distribution and is too
storage-constrained to simply install a second one alongside it.
Closing that gap meant designing a bespoke, non-ROS communication
layer from scratch (Chapter~\ref{ch:hardware-bridge}), not
configuring an existing one. Nav2's stock MPPI critic set is
documented and tuned against differential-drive and generic
holonomic platforms; it has no critic addressing the
late-turn-commitment behaviour this thesis found on an
Ackermann-steered vehicle with a wide minimum turning radius
(Section~\ref{sec:mppi-critic}). Nav2 also ships no fix for the
reversal-cusp K-turn freeze this thesis reproduced, diagnosed and
resolved with a custom smoother plugin (Section~\ref{sec:cusp-freeze}).
This failure mode is specific to tight-space Ackermann geometry, not
a defect in Nav2 itself.

This thesis's own contributions sit in five places:

\begin{itemize}
  \item the TCP/JSON bridge architecture connecting the navigation
    stack to a storage-constrained, ROS-incompatible onboard compute
    (Chapter~\ref{ch:hardware-bridge});
  \item \texttt{EarlyCommitCritic}, a custom MPPI critic plugin
    addressing Ackermann-specific late-turn commitment
    (Section~\ref{sec:mppi-critic});
  \item a custom path-smoother plugin resolving the reversal-cusp
    K-turn freeze (Section~\ref{sec:cusp-freeze});
  \item root-cause diagnoses of defects specific to this platform: a
    hardware-abstraction-layer buffering artefact misattributed to
    physical coasting (Section~\ref{sec:readmode-bug}), a LiDAR
    angle-convention bug (Section~\ref{sec:lidar-angle}) and a
    display-localisation timing artefact
    (Section~\ref{sec:display-lag});
  \item an empirical actuator-calibration methodology, throttle
    deadband characterisation and a steering-gain sweep, built for
    this vehicle rather than taken from a paper.
\end{itemize}

Together, these close the distance between the general-purpose tools
of Section~\ref{sec:state-of-the-art} and a working,
hardware-validated navigation system.

\section{Thesis Structure}
\label{sec:thesis-structure}

This thesis follows the two-phase methodology described in
Section~\ref{sec:motivation}. It begins by laying the technical
groundwork the navigation stack is built on, then develops and
validates that stack in simulation. From there it migrates the stack
to the physical QCar and works through the bridging, calibration and
integration issues that migration surfaced, before reporting and
reflecting on the results of both phases together. The remaining
chapters are structured as follows:

\begin{itemize}
  \item Introduces the technical foundations this thesis builds on:
        the ROS~2/DDS communication model, Ackermann steering
        kinematics, the Gazebo simulator and its ROS~2 integration,
        SLAM via Cartographer and the Nav2 stack's AMCL localisation
        and MPPI control components.
  \item Describes the simulation-side development of the navigation
        stack, including a recurring vehicle-dynamics bug pattern
        uncovered during testing of this drive architecture, then
        the full Nav2 stack's own end-to-end bring-up and validation
        in simulation, following the same teleoperation/SLAM/navigation
        phasing later applied on hardware.
  \item Presents the design of the TCP/JSON bridge that connects the
        ROS~2-based navigation stack to the robot's onboard compute,
        which cannot run that stack natively, including the odometry,
        LiDAR angle-convention and steering-trim fixes required to
        make the bridged sensor and actuator data trustworthy.
  \item Covers the identification of the vehicle's throttle response,
        including the static-friction deadband and the hardware
        abstraction-layer buffering defect that had been mistaken for
        physical coasting.
  \item Describes integrating and tuning the full Nav2 stack against
        the physical robot, including a custom MPPI critic plugin and
        AMCL parameter changes, culminating in closed-loop
        goal-reaching tests.
  \item Presents and quantifies the resulting gap between the
        simulated and physical phases across the project's diagnostic
        measurements.
  \item Answers the research questions posed above and reflects on
        what generalises beyond this specific platform.
\end{itemize}
